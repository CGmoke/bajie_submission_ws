# 题目二 · 正向运动学与坐标变换

> 解法说明与设计取舍。数值来自实测，出处标在文中，可在作品目录内复核。

## 一、这道题要交什么

给一组关节状态，算出夹爪 `objects_link` 相对底盘 `base_footprint` 的位姿；再把物体在底盘系里的位姿，换到夹爪系里去。两组结果都要带 `xyz`、`rpy`、`quat_xyzw`。

|---|---|
| 题号 | 题目二 |
| 源码 | `src/question2_project/`（`fk.py` 算正解，`solve_q2.py` 读写 JSONL，`verify_tf.py` 独立复核） |
| 输入 | `inputs/q2_demo_input.jsonl`，测例 `demo_zero` |
| 作答 | `answers/q2_demo_output.jsonl`，一行，两组位姿 |

## 二、题面要求对着做

| 题面 | 做法 |
|---|---|
| 算 `objects_link` 相对 `base_footprint` 的位姿 | 解析官方 xacro 展开后的 URDF，从 `objects_link` 沿父关节往上回溯到 `base_footprint`，得到一条有序链，再倒着相乘 |
| 把物体位姿换到夹爪系 | `T_objects_link^scene = (T_base^objects_link)^-1 · T_base^scene` |
| 说明链怎么读、变换怎么算、姿态怎么表示 | 见下节三小节 |
| 输出两组位姿 | 字段齐备，四元数落盘前归一，`rpy` 与四元数互推自洽 |

## 三、怎么做的

### 3.1 双轨：一条自己算，一条让它自己对

数学上这就是一串刚体变换相乘，没有玄机。真正容易出错的是三件事：链有没有取对、每一段按 URDF 语义拼得对不对、出来的姿态表示能不能自证。

干脆分成两条独立路线。主实现从 URDF 文本自己解析关节树，自己乘矩阵，全程不碰 TF；第二实现交给 ROS 2 的 `robot_state_publisher` 加 `tf2_ros`，让它算一遍同样的量，再回头比对。两套代码路径没有一处重叠：一边是我写的矩阵乘法，一边是 ROS 的 TF 树。它们同时对上，才有底气说结果是对的。只跑一条，错了自己也发现不了。

### 3.2 链怎么读

先建「子连杆 → 父连杆＋关节」的映射，从 `objects_link` 一路回溯到 `base_footprint`，把沿途的关节排成有序链，再倒序相乘。

每段的变换按 `T = T_origin · T_motion(q)` 构造。`T_origin` 取自关节的 `origin`（xyz 加 rpy，按 Rz·Ry·Rx 展开）；`T_motion(q)` 看关节类型，prismatic 沿 `axis` 平移 q，revolute 绕 `axis` 转 q。

有两个地方得留神。头部俯仰和两根手指是旁支，值要读进来，但不在这条链上；固定关节没有输入量，位置和朝向照样要算进去。这份模型 32 个 link、31 个 joint，每一段都得按 URDF 的父子关系取，不能照名字猜顺序。

### 3.3 变换怎么算

已知 `T_base^scene`（物体在底盘系，直接从输入拿）和 `T_base^objects_link`（刚算出来的夹爪位姿），物体在夹爪系里的位姿就是：

`T_objects_link^scene = (T_base^objects_link)^-1 · T_base^scene`

求逆没用通用 4×4 求逆。刚体变换的逆有解析形式：旋转矩阵转置，平移反投影（`R^T`、`-R^T t`）。既快，也不会引入额外的数值误差。

### 3.4 姿态怎么表示

内部一律用 4×4 齐次矩阵，只在输出时转成两种表示。

`rpy`：`pitch = asin(−R20)`，`roll = atan2(R21, R22)`，`yaw = atan2(R10, R00)`。

`quat_xyzw`：由旋转矩阵转四元数，按 `[x, y, z, w]` 顺序出，写文件前归一。

这两者必须互相对得上。四元数顺序写反、忘了归一、`rpy` 用错旋转次序，是这道题最常见的三种死法，光看数值还挺像那么回事。校验阶段特意做了一次互推比对，差多少一目了然。

### 3.5 为什么不用 TF 直接查

省事的写法是起一个 `robot_state_publisher`，用 `tf2_ros` 查 `base_footprint` 到 `objects_link` 的变换，一行代码出结果。

没这么干，理由有三。题面要「说明运动链的读取方式」，用 TF 等于把这段逻辑藏进 ROS 内部，答了跟没答一样。题目说的是「根据关节状态和模型计算」，纯计算不该背一个运行时依赖。更实际的一条：万一结果不对，用 TF 的话根本分不清是模型加载错了，还是自己算错了。

TF 就放在第二实现的位置，不产出，只负责打脸或者背书。

## 四、几个我认为值得一提的设计

**两套实现互相印证，比一套跑通有说服力。** 阈值定在 `1e-8 m` / `1e-7 rad`，三组用例（正式零位、只把 `lift_joint` 抬 0.1 m、弯臂且物体带 `rpy=[0.2,−0.3,0.5]`）实测位置和旋转误差都在 1e-15 量级。这个量级说明两套实现实际上在做同一件事，只是走了不同的路。

**把「位姿链自洽」做成可复算的判据。** 除了题面要的两组位姿，我还拿它们反推了一次：`T_base^scene` 应该等于 `T_base^grip · T_grip^scene`，跟输入里的 `scene_object_in_base_footprint` 逐项比。为什么值得多做这一步？万一变换方向写反（乘了正变换而不是逆变换），单看某一组数值可能「看着挺合理」，这条等式会立刻塌。等于给答案配了一个不依赖外部基准的自检。实测位置误差 0.0 m，旋转矩阵误差 1.9e-19。

**写文件之前先过一道格式门。** 每行作答落盘前查三件事：关节名齐不齐、位姿三个字段长度对不对、四元数模长是不是 1。任一不过，整轮停，旧文件不覆盖。JSONL 这种格式，少个字段、多个逗号、四元数没归一，都足以判 0 分，而且错在本地暴露比错在评审打开文件那一刻要好得多。实测三组位姿的四元数模长都是 1.000000000000。

**求解和复核解耦。** `solve_q2.py` 只依赖 Python 与 NumPy，`--verify` 才拉 ROS。没装 ROS 的人照样能复现作答；装了的人可以多验一层。同一份代码伺候两种场景，不必要求所有人先装一整套。

## 五、验证到哪一步

| 项 | 结果 |
|---|---|
| 输出字段 | `id`、`objects_link_in_base_footprint`、`scene_object_in_objects_link` 齐全 |

| 耗时 | 求解 < 5 秒 |

## 六、没解决的和不好办的

关节只支持 revolute、prismatic、fixed 三类，几何只认 mesh、box、cylinder、sphere 四种。碰上 `planar` 或 `floating` 得另写。

平坦零位附近，`rpy` 的 `yaw` 对数值噪声很敏感（本例在 1e-8 量级）。下游若要按 `rpy` 卡阈值，建议改用四元数或旋转矩阵。

模型里有 `mimic` 关节（比如联动的手指）时，当前按「输入已经给了每个关节的实际值」处理，不做联动推导。题面给了全部十个关节值，所以不构成问题；哪天真只给一部分，这里会失效。
