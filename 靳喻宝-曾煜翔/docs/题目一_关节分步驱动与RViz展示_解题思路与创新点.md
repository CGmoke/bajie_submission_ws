# 题目一 · 关节分步驱动与 RViz 展示

> 解法说明与设计取舍。所有数值都能在作品目录里复核，出处标在文中。

## 一、这道题要交什么

题目要的是五段动作：升降、头部俯仰、机械臂、夹爪张开、夹爪闭合。每段做完，记下十个关节的当前值；前三段结束后停一会儿（`pause_sec`，默认 5 秒）。

| 项目 | 内容 |
|---|---|
| 题号 | 题目一 |
| 源码 | `src/question1_project/`（`bajie_tasks` 包含驱动节点 `q1_drive` 与净空模型 `q1_safety`） |
| 输入 | `inputs/q1_demo_input.jsonl`，测例 `q1_all_seed7` |
| 作答 | `answers/q1_demo_output.jsonl`，一行，五个关键帧 |
| 演示 | `video/q1_rviz.mp4` |

麻烦的地方不在「让关节动起来」。动起来容易，难的是让另一个人在你的机器之外跑出同样的结果，还能指着一行日志说「这就是那一帧」。

## 二、题面三条，分别怎么对应

| 题面 | 做法 |
|---|---|
| 依次展示五个阶段 | 节点按 `lift → head → arm → gripper_open → gripper_close` 顺序插值，一段只动本段关节，其余不动；加 `--gui` 时 launch 顺带拉起 `robot_state_publisher` 和 RViz |
| 前三段各停 `pause_sec` | 三个阶段收尾处各调一次 `hold(pause_sec)`，原地保持并持续发状态。夹爪张开到闭合之间不插停顿 |
| 每段记十个关节 | 段末把 `lift_joint`、`pitch_joint`、`joint1`–`joint6`、两根手指的当前值原样写进关键帧 |

## 三、怎么做的

### 3.1 把它当成状态机，而不是一次表演

整条链路只有五步：读输入，用 `seed` 抽样出目标位姿，逐段插值，段末快照，跑完一次性写文件。没有回读，也没有反馈修正。既然如此，设计的重心就不该放在算法上，得放在「同一个输入能不能稳定得到同一个输出」上。

发布端只有一个：`/joint_states` 由 `q1_drive` 独家发布，`robot_state_publisher` 只订阅、发 TF，RViz 只画。这一点是刻意的。要是同时把 `joint_state_publisher_gui` 拉起来，两个节点会按各自的节拍往同一话题写，画面会抖，更要紧的是——关键帧里那几个数，到底对应哪一次发布？没人答得上来。

### 3.2 几个容易翻车的细节

抽样口径。每个阶段的目标值由 `random.Random(seed)` 对九个预设区间依次均匀抽样，统一保留 6 位小数。不掺系统时间，不读环境变量，不依赖全局随机状态。换台机器，同一 `seed` 给出的十个关节值一模一样。

插值和节拍。段内走 smoothstep，起止速度为零，段与段之间不会出现关节突跳。发布固定 30 Hz，用 `time.sleep(1/publish_hz)` 控制，不用 `create_rate()`：循环里没有 `spin`，定时器会被阻塞。

保持段。`hold()` 不插值，只按同一节拍重复发当前状态。它不是为了「看着舒服」，是为了让「阶段完成」和「关键帧快照」落在同一个稳定态上。

净空量什么。用官方 URDF 的可视与碰撞几何拼出每个连杆的局部包围盒，正向算位姿，再逐段量两个下界：离 `base_footprint` 下方 z=0 地面多远，离非相连机身多远。这里有个坑，下面单独说。

### 3.3 净空的两种数值，别混着看

同一个模型会吐出两个数：整段运动的保守下界，和关键帧那一瞬的静态几何下界。前者把「这一段里任一点可能移动的距离」也扣掉了（旋转关节按半径乘转角估算），后者只算那一刻。

| 阶段 | 整段保守（地面 / 机身） | 该帧静态（地面 / 机身） |
|---|---|---|
| lift | 0.514 / −0.200 | 0.759 / 0.044 |
| head | 0.759 / 0.044 | 0.759 / 0.044 |
| arm | −0.807 / −0.407 | −0.056 / 0.006 |
| gripper_open | −0.070 / 0.006 | −0.054 / 0.006 |
| gripper_close | −0.070 / 0.006 | −0.056 / 0.006 |

臂段那个 −0.807 看着吓人，其实几何只占 −0.056，其余全是运动余量。夹爪实际只探到地面以下 5.6 厘米，跟 RViz 里看到的一致。只看一个数就会误判：看保守值，像是机械臂扎进地里 80 厘米；看静态值，又丢了「整段插值会不会蹭到」的信息。

### 3.4 净空为什么只报警、不拦

最初写的是硬拦：低于 5 厘米 / 2 厘米就拒绝播放。跑起来才发现，官方 `q1_all_seed7` 的示例位姿自己就不达标。要真拦，作答就跟官方公布的关键帧对不上，等于用自定阈值否掉了题面的标准答案。

改成两档：阈值判断留着，做成开关（`certify(enforce_ground=…, enforce_body=…)`），题一驱动显式传 `False`，数值照样进日志。姿态没改，证据还在，只是不再拿它当闸门。包围盒重叠不等于网格相交，这句话也写进了文档，免得有人把几何估计当成物理碰撞。

## 四、几个我认为值得一提的设计

**抽样口径钉死，才算真能复现。** 很多实现直接调全局 `random`，或者吃 `numpy.random` 的默认状态。同一 `seed` 在不同版本、不同调用顺序下，序列可能就不一样了。把随机源、抽样顺序、区间、精度四样全固定下来，跨机器逐字节一致才不是碰运气。实测作答与官方示例的十个关节逐值比对，误差 0.0e+00；文件哈希 `6e7db6ba…dc2081`，反复重跑没变过。

**两种口径分开报，比报一个数诚实。** 只给保守值，读者会被 −0.807 吓住，然后去核视频，发现对不上，接着怀疑整份材料。只给静态值，又漏掉了插值过程的风险。分开列，读者自己能判断该信哪个。

**单一状态源，让关键帧、TF、画面三者天然对齐。** 这不是架构洁癖。两个发布者在场时，日志里的值和屏幕上的姿态可能差一帧，而这一帧恰好就是评审要核对的那一帧。

**写完再交，别边跑边写。** 演示类程序最容易死在「跑到一半被打断」：手动 Ctrl-C、RViz 崩、机器卡。边跑边写，交出去的可能就是半份。原子写出让「文件存在」等价于「这一轮完整跑完」，题二、题三用的也是这一手。

## 五、验证到哪一步

| 项 | 结果 |
|---|---|
| 关键帧 | 5 个，顺序 `lift → head → arm → gripper_open → gripper_close` |
| 关节字段 | 每帧 10 个齐全，全部落在 URDF 限位内 |
| 最终状态 | 与最后一帧逐值相等 |
| 与官方示例 | 十关节逐值一致，误差 0.0e+00 |
| 可复现 | SHA-256 `6e7db6ba…dc2081`，多次重跑一致 |
| 耗时 | 约 30 秒（五次移动各 3 秒，三次保持各 5 秒） |
| 视频 | `video/q1_rviz.mp4`，976×720 / 25 fps，888,772 字节 |

## 六、没解决的和不好办的

净空是包围盒估计，不是物理仿真。包围盒压在一起，网格未必相交；反过来也一样。所以它只能提示「这里值得看一眼」，不能当安全结论。

判据目前写死：十个关节、五个阶段。题面要是扩到别的阶段或可变关节集合，阶段表和抽样区间就得挪到配置里去。

保持段按时间算，不按帧数算。录制机器性能差一点，就可能丢帧；改成「保持 N 个发布帧」更稳。
